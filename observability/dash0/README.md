# Dash0: Debrief health dashboard, SLOs and browser RUM

Debrief sends three kinds of telemetry to Dash0:

- **The API** (`debrief-api`, `api/telemetry.py`) sends traces, logs and metrics:
  - `debrief.playlist.duration`, `debrief.playlist.empty`, `debrief.llm.tokens`, `debrief.memo.citations_dropped` and `debrief.memo.lines`.
  - Product metrics: `debrief.playlist.tool_requests` (by `tool`), `debrief.playlist.clip_labels` (by `label`), `debrief.rerank.batches` (by `outcome`), `debrief.memo.duration` (ms, by `outcome`), `debrief.cache.lookups` (by `route`, `result`; only with `DEBRIEF_CACHE=on`) and `debrief.playlists.shared`.
  - The FastAPI instrumentation's `http.server.duration` (ms, by `http.target` route template, `http.method`, `http.status_code`) and `http.server.active_requests`. Probes are excluded.
  - One structured log per product event (section 5) and one access log line per request, each on its request's trace.
- **The browser** (`debrief-web`, `web/src/rum.ts`) sends page views, web vitals, JS errors, one span per `fetch`, and custom events for product actions. Same-origin `/api/*` requests carry `traceparent`, so in Dash0 a browser request span is the parent of the API trace it caused.
- **The ingest job** (`debrief-ingest`) sends its own traces.

None of these carry transcript text, the pain sentence, prompts or keys.

| File | What it is |
| --- | --- |
| `debrief-health.dashboard.yaml` | The "Debrief health" dashboard as a Perses `PersesDashboard` CR. Use it with the Dash0 CLI, the operator or Terraform. |
| `debrief-health.dashboard.json` | The same dashboard as Perses JSON, for the UI's **Edit as JSON**. Generated by `uv run python observability/dash0/to_json.py`; a test keeps it equal to the YAML. |
| `slo-playlists-fast.openslo.yaml` | SLO (a), "Playlists come back fast": 95% of production `/api/playlist` requests under 5 s. |
| `slo-memo-citations.openslo.yaml` | SLO (b), "Memo lines carry a valid citation": at least 99% of memo lines aren't dropped. |
| `to_json.py` | Rebuilds the JSON from the YAML. |

`tests/test_dash0_assets.py` checks four things: the JSON matches the YAML, every panel is placed on the grid, every `debrief.*` metric a query names is one the API exports, and the SLO files use the shape Dash0 accepts.

## 1. Turn on browser RUM (one-time, about 3 minutes)

The browser reads its Dash0 settings at runtime from `GET /api/config`. No token is ever in git or in the image. Until `DASH0_WEB_TOKEN` exists, `/api/config` returns `{"rum": null}` and the page loads no SDK at all.

1. In Dash0, open **Organization Settings › Auth Tokens** and create a token:
   - Name it `debrief-web`.
   - Set permissions to **Ingesting** only.
   - Limit it to the dataset the API uses (`default`).

   This is a "website" token. Dash0 designs these to be visible in the page, which is why it is ingest-only and separate from the backend token.
2. Add it to the Kubernetes Secret `app-credentials` under the key `dash0-web-token`, alongside the existing keys. This is the same Secret, created by hand, as `README.md` › Deploy describes. `deploy/deployment.yaml` already maps that key to `DASH0_WEB_TOKEN`, as `optional: true`, and sets `DASH0_WEB_ENDPOINT=https://ingress.us-west-2.aws.dash0.com`.
3. Restart the `app` Deployment, for example with Radar `manage_workload` restart, because env vars from Secrets are only read at pod start.
4. Check it:
   - `curl -s https://brogrammers.cnh.radarhq.io/api/config` returns a `rum` object.
   - In the browser's dev tools, the page loads a `dash0-*.js` chunk and POSTs to `https://ingress.us-west-2.aws.dash0.com/v1/logs` and `/v1/traces`.

For local work, put `DASH0_WEB_TOKEN` (and optionally `DASH0_WEB_ENDPOINT`) in `.env`, then run `make api` and `make web`.

**What the browser sends:**
- Instrumentations: `@dash0/navigation`, `@dash0/web-vitals`, `@dash0/error`, `@dash0/fetch` and `@dash0/xhr`.
- Session replay and frustration signals stay off, because rage-click events report the clicked element's text, which can be a transcript quote.
- Product actions are custom events (`sendEvent`) from one document-level click listener on `[data-rum-event]`:

  | `data-rum-event` | Attributes sent |
  | --- | --- |
  | `watch_click` | `rank` (from `data-rank`), `clip_id` (from `data-clip-id`) |
  | `memo_copy`, `memo_make`, `playlist_build` | none |

  No element text is ever read.
- Every signal carries `deployment.environment`, `service.version` and resource `service.name=debrief-web`.

## 2. Import the dashboard

Choose one of three ways:

- **UI:**
  1. Open **Dashboards** and click **+ Add**.
  2. At the top right, click **Edit as JSON**.
  3. Paste or upload `debrief-health.dashboard.json`.
  4. Click **Apply**, then save.
- **CLI:** `dash0 apply -f observability/dash0/debrief-health.dashboard.yaml`. This needs a token with write access, and `metadata.labels["dash0.com/id"]` makes repeated applies update the same dashboard.
- **Terraform:** a `dash0_dashboard` resource with `dashboard_yaml = file("observability/dash0/debrief-health.dashboard.yaml")`.

## 3. Create the two SLOs

**As code** (needs an auth token with **All permissions**):

```sh
dash0 apply -f observability/dash0/slo-playlists-fast.openslo.yaml
dash0 apply -f observability/dash0/slo-memo-citations.openslo.yaml
```

Terraform works too: a `dash0_slo` resource with `slo_yaml = file(...)`. The `dash0.com/origin` label makes applies idempotent, and it makes the SLO read-only in the UI.

**In the UI** (needs the **Create SLO** permission):

1. **SLO (a): Playlists come back fast**
   1. Open **Alerting › SLOs**. Open the menu next to **Create with Agent0** (**More create options**) and choose **Manually**.
   2. For the SLI shape, choose **Good / Total**.
   3. Turn the **counter** flag **off**. The latency comes from a native histogram, so the queries are expressions, not bare counters.
   4. Paste the **good** query:
      ```
      histogram_fraction(0, 5000, sum(increase({otel_metric_name="debrief.playlist.duration", otel_metric_type="histogram", deployment_environment_name="production"}[5m]))) * histogram_count(sum(increase({otel_metric_name="debrief.playlist.duration", otel_metric_type="histogram", deployment_environment_name="production"}[5m])))
      ```
   5. Paste the **total** query:
      ```
      histogram_count(sum(increase({otel_metric_name="debrief.playlist.duration", otel_metric_type="histogram", deployment_environment_name="production"}[5m])))
      ```
   6. Set the target to `0.95`. The window is fixed at rolling 28 days.
   7. Set the name to `Playlists come back fast` and the description to `95% of production /api/playlist requests (rerank on) finish in under 5 s.`
   8. Save. The SLO appears in **Alerting › SLOs** with a **New** badge and shows data after a few minutes.
2. **SLO (b): Memo lines carry a valid citation**
   1. Choose **Manually** again. For the SLI shape, choose **Bad / Total** and leave **counter on**.
   2. Paste the **bad** query:
      ```
      {otel_metric_name="debrief.memo.citations_dropped", otel_metric_type="sum", deployment_environment_name="production"}
      ```
   3. Paste the **total** query:
      ```
      {otel_metric_name="debrief.memo.lines", otel_metric_type="sum", deployment_environment_name="production"}
      ```
   4. Set the target to `0.99`, the name to `Memo lines carry a valid citation`, and the description to `At least 99% of memo lines cite only clips the team requested.`
   5. Save.
3. **Optional alert:** Dash0 raises no alert by itself when an SLO burns its budget. On each SLO's page, use **Create check rule**, which alerts on the `dash0.slo.burn_rate.fast` metric.

### Why 5 s

All figures below were measured on 2026-11-09 from `debrief.playlist.duration` in Dash0 and from a live run against the real index and model.

| Sample | p50 | p95 | Under 5 s |
| --- | --- | --- | --- |
| 20 sequential live playlists with rerank, client-side, local API | 3.29 s | 3.95 s | 100% (max 3.97 s) |
| Dash0, last 20 min, after the rerank latency fix | | 4.75 s production, 4.85 s local | |
| Dash0, last 1 h, includes traffic from before the fix | | ~9.8 s production | 81% production, 94% local |

5 s sits just above the post-fix p95. It is also a bucket boundary of the histogram's default buckets (…, 2500, 5000, 7500, 10000 ms), so the good count is exact rather than interpolated.

There is a risk: the 28-day window includes the pre-fix traffic, so the error budget starts partly spent. If 5 s proves too tight, 7.5 s is the next exact boundary. The change is one number in both queries.

### Why a new counter for SLO (b)

`debrief.memo.citations_dropped` alone has no denominator. The kept-line counts were only span attributes, which PromQL can't sum. So `api/memo.py` now records `debrief.memo.lines` once per memo: every line the citation check looked at, kept or dropped. A test in `tests/test_telemetry.py` covers it.

Until this change is deployed, production has no `debrief.memo.lines`, and SLO (b) shows no data. Locally it is already in Dash0: 46 lines and 0 dropped.

## Assumptions about Dash0 PromQL naming

These assumptions were checked against Dash0's docs and the live dataset on 2026-11-09:

- **Metric selectors use `{otel_metric_name="<OTel name>", otel_metric_type="histogram|sum"}`.** Dash0 recommends this style, and it is stable across unit changes. Dash0 also serves the Prometheus-translated names, which the live dataset confirmed: dots become underscores, a unit suffix is added for real units, `_total` is added for counters, and curly-brace units are dropped:
  - `debrief_playlist_duration_milliseconds_bucket`
  - `debrief_llm_tokens_total`
  - `debrief_memo_lines_total`
- **Histograms come back as native histograms** when selected via `otel_metric_name`. So `histogram_quantile` and `histogram_fraction` work without `sum by (le)`, and there is no `le` label. That is why SLO (a) uses Dash0's documented native-histogram pattern instead of `le="5000"`.
- **Attribute and resource labels have dots replaced with underscores:**
  - `service.name` becomes `service_name`
  - `http.route` becomes `http_route`
  - `deployment.environment.name` becomes `deployment_environment_name`

  All three were confirmed on live series.
- **API traffic comes from Dash0's span metric `dash0.spans`,** filtered by `otel_span_kind="SERVER"` and grouped by `http_route`. `otel_span_status_code="ERROR"` marks 5xx responses.
- **Browser custom events become `dash0.web.events`,** with `event.name` as `event_name` and the `rank` attribute as `rank`. This follows Dash0's synthetic-metric docs, but it is **not yet confirmed against live data** (see the table above).
- **App and browser metrics use a fixed `[1h]` window, not `$__rate_interval`.** The SDK exported metrics every 60 s, so Dash0's short automatic window often held a single sample and `rate()`/`increase()` returned nothing (empty panels, lone spikes). The deployment now sets `OTEL_METRIC_EXPORT_INTERVAL=10000` (10 s), and the panels read 1-hour windows: each point summarises the hour before it, so lines stay continuous between bursts of traffic and counts read "in the last hour". Only the `dash0.spans` panels keep `$__rate_interval`, because Dash0 produces that metric itself at fine resolution.
- **`http.server.duration`** comes from the FastAPI instrumentation with the old HTTP semantic conventions (the default), so its labels are `http_target` (the route template, e.g. `/api/playlists/{playlist_id}`), `http_method` and `http_status_code`. Request counts per route are `histogram_count(rate(...))` of that native histogram. Not yet confirmed against live data.

## 5. Event logs and access logs

Every product event is one log line through Python `logging` (logger `debrief.events`, `telemetry.log_event`). The body reads `event=<name> key=value ...`. The same fields are attributes `debrief.<key>`, next to `event.name`, so the Logs explorer can filter with `event.name = playlist.served` and group by any field. Each line carries its request's trace id. Fields are ids, counts, durations and fixed enums only: never the pain sentence, transcript text, memo lines, prompts, keys, or names of unknown packages.

| `event.name` | Level | Fields |
| --- | --- | --- |
| `playlist.served` | INFO | `tools` (catalog ids, else `other`), `clip_count`, `talk_count`, `total_seconds`, `filter`, `rerank`, `elastic_rerank`, `model_rerank` (the `debug.rerank` statuses), `duration_ms`, `cache` (`hit`, `miss`, `off`) |
| `rerank.batch` | INFO, WARN if it fell back | `index`, `size`, `outcome` (`ok`, `fallback`, `timeout`), `error` (error type), `duration_ms` |
| `rerank.partial` | WARN | `failed`, `batches`, `outcomes`, `imputed` |
| `rerank.model_fallback` | WARN | `error`, `clips_sent` |
| `rerank.elastic_fallback` | WARN | `reason` (`timeout`, `error`), `timeout_ms` |
| `memo.made` | INFO | `tools`, `clip_count`, `cited_count`, `dropped_lines`, `duration_ms`, `tokens`, `input_tokens`, `output_tokens`, `cache` |
| `memo.failed` | WARN | `clip_count`, `error`, `duration_ms` |
| `stack.parsed` | INFO | `file_type`, `package_count`, `matched_tools`, `unknown_count`, `tools`, `picked` |
| `playlist.shared` | INFO | `id`, `clip_count`, `source`, `filter` |
| `playlist.loaded` | INFO | `id`, `found`, `clip_count` |
| `insights.read` | INFO | `requests`, `playlists_saved`, `top_tools`, `empty_tools`, `cache` |

**Access logs.** uvicorn's `uvicorn.access` logger doesn't propagate to the root, so `telemetry.setup()` puts the OTel log handler on it directly (only when an endpoint or `DEBRIEF_OTEL_CONSOLE=1` is set). Each request line, e.g. `127.0.0.1:52144 - "POST /api/playlist HTTP/1.1" 200`, reaches Dash0 with the request's trace id. A logging filter drops `/healthz` and `/readyz`, so probes stay out of both the pod log and Dash0.

## Known gaps

- The first `/api/tools`, `/api/talks` and `/api/version` calls on page load start before the SDK finishes loading, so they have no browser span. They still have their API trace. Every later call, including playlist, memo and clip text, is linked.
- `web/src/version.ts` still adds its own `traceparent`. With RUM on, the SDK appends a second one to that one request, and the API then starts a fresh trace for `/api/version`. Drop `withTrace()` there once RUM is live.
- The `data-rum-event` attributes come from the web restyle. Until that lands, only the delegation and its tests exist.
